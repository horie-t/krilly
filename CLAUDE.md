# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Krilly is a **holonomic (3 omni-wheel, "kiwi drive") Micromouse** running on a Raspberry Pi 5, targeting the classic 16×16 Micromouse competition. Work is organized into milestones **M0–M6**: 足場(scaffold) → HAL bring-up → 運動学(kinematics) → 自己位置推定(localization) → 迷路+知覚(maze+perception) → 探索+最速(search+speed) → 統合(integration).

Code comments and docstrings are written in **Japanese** (technical terms, identifiers, register names, and formulas stay in English). Keep new comments consistent.

## Hardware / toolchain

- Raspberry Pi 5 (Raspberry Pi OS), Python ≥ 3.11.
- 3× stepper motors + 3× **L6470** (dSPIN) drivers over **SPI0** (mode 3), daisy-chained on one CS (CE0); single-driver control also supported.
- **BNO055** 9-axis IMU over **I2C** (address 0x28, bus 1). Pi 5's RP1/DesignWare I2C handles clock stretching correctly (unlike Pi 1–4), so 100 kHz works — no `i2c_arm_baudrate` reduction needed.
- Pi **Camera Module V3** (wide), mounted downward, via **picamera2** (`cv2.VideoCapture` does not work on the libcamera stack). Used to detect the **red wall-tops**.
- Hardware-only deps (`spidev`, `lgpio`, `picamera2`) are `aarch64`-gated in `pyproject.toml` and lazy-imported; `smbus2`/`numpy`/`opencv-python`/`pyyaml` are always installed so pure-logic code and tests run on any machine.

Raspberry Pi 5 enablement (SPI/I2C/camera): see `docs/setup-pi5.md`.
Competition-day procedure (what to check before a run, how to read the exposure line, what to do when the venue is dark): see `docs/venue-checklist.md`.

## Architecture

Layered under `src/krilly/` (low → high level; each layer is independently testable):

- `hal/` — hardware abstraction: `l6470` (single driver) / `l6470_chain` (3× daisy-chain) over SPI; `imu` (BNO055/I2C); `gyro_sampler` (`GyroSampler`: samples gyro z on its own thread and integrates every sample, so the 50 Hz control loop stops throwing half the chip's output away, #81); `camera` (picamera2 → BGR frames).
- `kinematics/kiwi.py` — `KiwiKinematics`: forward/inverse kinematics + wheel-speed ⇄ stepper conversion.
- `motion/velocity_driver.py` — `VelocityDriver`: rate-limits body velocity (trapezoidal ramp), then commands all 3 wheels in one `run_all`. Ramping in *body* space keeps the wheel-speed ratio constant, so the path holds during accel (L6470's per-device ACC alone would skew it). `update(dt)` is pure computation — no sleeps; the caller drives the loop.
- `motion/corner.py` — the geometry of turning **without stopping** (#80): the blend distance `v²/2a`, the shape of the rounded corner, and how much room it leaves against the posts. Pure functions, no state; `tuning.check_limits` uses them to refuse a blend that would not fit.
- `motion/cell_motion.py` — `CellMotion`: closed-loop **1-cell translation (any of the 4 body directions) / 90° turn** primitives (M4 #17, M6 #76), plus **chained legs with rounded corners** (`queue_move` / `start_path`, #80). `start_move(distance, axis_quarter_turns)` picks the primary axis; `start_forward*` are thin wrappers with `axis_quarter_turns=0`. Holds an *ideal lattice* reference pose and drives the estimated pose to it, so per-move residuals don't accumulate across cells. Primary axis follows a `sqrt(2·a·remaining)` decel envelope (clamped to the `VelocityDriver` ramp so it stays followable) with a **minimum-speed floor** so the tail of the envelope doesn't stall on static friction; the other DOFs are P-held (translation: cross-track + heading; turn: X/Y). Terminates on *remaining*, then settles and re-tries once at creep speed if it coasted past. `update(dt, gyro_rate=…)` is pure computation and also integrates the estimator. On hardware the final residual sits at roughly the **termination tolerance**, so `pos_tol_m` / `angle_tol_rad` are the knobs that set accuracy (keep `floor · dt ≤ 2 · tol` so a floor-speed tick cannot jump the band).
- `localization/` — `estimator.py` (`DeadReckoning`: `[X, Y, φ]`, midpoint integration, pluggable input: commanded speeds / microsteps / distances) and `grid.py` (`GridCorrector`: snap X/Y to the 180 mm grid with a `max_error` guard; `apply_cell_offset`: pull the estimate onto a camera-measured intra-cell position).
- `perception/` — `red_wall.py` (red wall-top detection: two-range HSV mask → contour centroids), `wall_detect.py` (`WallDetector`: per-edge ROI red *fraction* → walls present front/back/left/right, then `body_walls_to_maze()` → `Maze`; with `calibrated_config(neighbors=True)` it also reads the **E/W neighbours' four walls** from six more ROIs placed by the same geometry, `neighbor_walls()` → tri-state per edge, #89), `survey.py` (the calibration-data layer, #78: one CSV row per frame-and-slot with the measured red fraction and the *ground-truth* label; `label_run` labels a whole run's frames **after** it finishes, from the map it ended with — `summarize`/`format_report`/`compare` then turn that into the per-edge distribution, the separation margin and the miss/false-alarm counts), `axis_yaw.py` (`axis_yaw`: yaw from the *orientation* of the red wall-top edges — gyro-independent heading truth, see below) and `cell_pose.py` (`cell_offset`: where the machine sits *inside* the cell, from how far the red bands moved — the absolute position fix odometry cannot provide).
- `solver/maze.py` — `Maze` / `Direction`: 16×16 grid with **shared-edge walls** (cell A's east wall *is* cell B's west wall, so they can never disagree), outer walls, centre-2×2 goal, `to_ascii()`.
- `strategy/` — `flood_fill.py` (`flood_fill`: 4-neighbour BFS distances from the goal cells, `UNREACHABLE` for walled-off cells; `next_direction`: descend the gradient, tie-broken by *unvisited → fewest quarter-turns → N/E/S/W* so it's deterministic), `explorer.py` (`Explorer`: observe walls → re-flood → next `Step(direction, to_cell)`, plus the maze↔world bridge `heading_rad` / `cell_center` / `quarter_turns`; `holonomic=True` keeps `facing` fixed and tracks `travel` = the last direction moved; `known` = cells whose **four walls were all observed** and `plan_leg(n)` = the steps that can run as one motion without stopping, #89) and `shortest_path.py` (`shortest_path`: Dijkstra over *(cell, previous direction)* restricted to `known` cells, weighted by a `MoveCost(cell_ns, cell_ew, leg, turn)`; `path_to_legs` run-length-encodes it into `Leg(direction, cells)` for the speed run. `DEFAULT_COST` is turn-free, `LEGACY_COST` reproduces the old turn-weighted search exactly). All discrete and hardware-free, so a whole search run can be simulated off-Pi against a ground-truth `Maze` (see `tests/test_explorer.py`).
- `app/` — `run_manager.py` (`RunManager` / `RunPhase`: the WAIT → SEARCH → RETURN_HOME → SPEED → … state machine under the classic **7-minute / 5-run** budget (rule 3-6; M5 #20). Counts a *run* as a departure from the start square toward the goal — the search is run 1, returns are free. It only *starts* a run when the remaining time covers the (return + speed) estimate × `time_margin`; the estimate counts N/S cells, E/W cells and legs separately (and turns too when `holonomic=False`), so re-measure those if speeds change. Pure logic — `now` is passed in, so the whole session simulates in tests. `scripts/speed_run.py` drives it: search like `search_run`, then executes `Leg(direction, cells)` lists with **multi-cell straights in one motion**, path-check + confidence-gated position correction at every leg boundary).
- `sim/` — **hardware-free simulation of a whole competition session** (#77): `excerpt.py` (cut an N×N out of a transcribed contest maze and score how much of it can only be tested on hardware — `longest_blind_cross_run` is the one that matters, #23/#85), `sense.py` (`sense`: the camera's stand-in — reads body-relative walls off a ground-truth `Maze`; the exact inverse of `body_walls_to_maze`; `sense_neighbors` does the same for the E/W neighbours), `generate.py` (`random_maze` = spanning tree + loops, plus `open_maze` / `serpentine_maze` / `comb_maze` / `seal_goal` / `diagonal_goal` as adversarial cases), `check.py` (`check_maze`: outer closed / goal reachable / bare posts / boxed cells, and `wall_counts` for "can I physically build this?"; `map_agrees` compares the learned map against truth **over the visited set**), `session.py` (`simulate_session`: SEARCH → RETURN → SPEED ×N driven by `RunManager` with `estimate_s` as the clock). `scripts/maze_sim.py` runs many mazes and exits non-zero on a problem. Maze data in `mazes/` (see its README for the ASCII format), including **31 real All-Japan mazes 2010–2024** in `mazes/contest/`, transcribed from the record-book figures by `scripts/maze_from_image.py` (#84).
- `config/` — `robot.yaml` / `maze.yaml` + typed loader (`RobotConfig`, `MazeConfig`).
- `logging_config.py` — `setup_logging` / `get_logger`.

`scripts/` = per-peripheral bring-up CLIs. `tests/` = pure-logic unit tests with faked transports.

### Conventions & gotchas (read before touching HAL / kinematics)

- **Testable-HAL pattern**: every HAL class takes an injectable transport (`spi=` / `serial_obj=` / `bus=` / `picam2=`); tests pass a fake and assert the exact byte/register stream. The real transport is opened (and its hardware lib lazy-imported) only when the arg is omitted. Follow this for new HAL so it stays unit-testable off-Pi.
- **Coordinate frame** (`docs/coordinate-frames.md`, `config/robot.yaml`): body **+x forward, +y left, +z up** (right-handed), **+ω = CCW**. Wheels/motors: **M0 front, M1 rear-left, M2 rear-right**; L6470 device index *i* = motor M*i* = wheel W*i* (daisy-chain wired M0→M1→M2, index0 nearest MOSI).
- **`wheel_angles_deg` holds SPOKE angles `[0, 120, 240]`, not drive directions.** The IK formula `v_i = -sinθ·vx + cosθ·vy + L·ω` takes θ = spoke angle (wheel *position*); the drive direction is θ+90° = `[90, 210, 330]°`. Putting drive-direction angles in the config rotates all translation by 90° while rotation still looks correct — the exact symptom seen on hardware (#11). If forward/strafe are swapped but ω is fine, suspect this, not the wiring.
- **Maze grid vs body frame**: `solver/maze.py` cells use **east=+x, north=+y** with `Direction` N/E/S/W; that is separate from the body frame above. `perception.wall_detect.body_walls_to_maze()` maps body-relative walls to maze directions via the robot's facing. The metric bridge lives in `strategy/explorer.py`: cell (x, y) centre = `(x·pitch, y·pitch)` and **N=+90° / E=0° / S=−90° / W=180°**, so the start pose (cell (0,0) facing north) is `[0, 0, +π/2]` — not φ=0.
- **A simulated maze is only as hard as you made it, and the two easy mistakes pull in opposite directions** (#77, `krilly.sim.generate`). Random mazes are generated as a spanning tree, then walls are opened to make loops; `loop_ratio` controls how many. Measured on 16×16 over 8 seeds (interior walls cap at 225): `0.0` → 225 walls, search 26–168 steps; `0.10` (the default) → 190–195 walls, 14–37 steps; `0.35` → 142–152 walls, **median 14 steps = the Manhattan minimum, i.e. the mouse never once hits a dead end**. A sparse maze is not a test of the search. But `loop_ratio=0` overshoots the other way: a DFS-carved perfect maze has the "river" property and its *own solution* ran 169 cells on a 16×16, which no competition maze does (real ones are ~40–80). Neither extreme is realistic, and **a generated maze is easier than a designed one at any density** — that is why transcribing real mazes (`mazes/README.md`) is a separate task, not a nice-to-have.
- **The safety margin was set to 1.5 on no evidence, and it sat on a cliff** (#87, `RunManager.time_margin`, now **1.2**). It gates only one decision — whether to *start* a run — and getting it wrong in the safe direction means **refusing a race the machine could have won**. Rule 3-1 makes the record the fastest single run, so a speed run that runs out of time costs only the time, and the earlier record stands: **refusing is the expensive error.** Sweeping margin against `actual_scale` (how much slower reality is than the estimate) over the contest mazes — `maze_sim --maze mazes/contest/*.txt --budget-sweep`, 30 of the 31 (one is excluded by the sanity check, #84) — counting mazes that get no speed run at all / total speed runs / sessions that overrun the 7 minutes:

  | margin | 1.0× | 1.1× | 1.2× | 1.4× |
  |---|---|---|---|---|
  | **1.5** | 7/30, 30, 0 | 8/30, 27, 0 | 9/30, 24, 0 | 12/30, 19, 0 |
  | **1.4** | 3/30, 37, 0 | 7/30, 28, 0 | 8/30, 26, 0 | 10/30, 21, 0 |
  | **1.3** | 3/30, 38, 0 | 4/30, 34, 0 | 7/30, 28, 0 | 9/30, 22, 1 |
  | **1.2** | 3/30, 38, 0 | 3/30, 36, 0 | 4/30, 31, 0 | 9/30, 22, 1 |
  | **1.1** | 2/30, 42, 0 | 3/30, 37, 0 | 4/30, 31, 0 | 9/30, 23, 2 |
  | **1.0** | 0/30, 46, 0 | 2/30, 39, **2** | 4/30, 34, **3** | 9/30, 23, 2 |

  **1.2 beats 1.5 in every column** — fewer mazes shut out, more races run (38 against 30), and still zero overruns when reality is 20 % slower than the estimate. The measured estimate error is **0.5 %** (#23: search 33.3 s against 33.1, speed 21.7 against 21.6), so 20 % is 40× the observed error. 1.0 is a step too far: it overruns on 2 mazes when reality is only 10 % slower. And **1.5 was sitting right on a cliff** — merely dropping to 1.4 lets four more mazes race (2011 exp-q, 2013 exp-fin, 2018, 2022), which is what a value chosen without measurement looks like. The 3 mazes still shut out at 1.2 (2014/2015/2017 exp finals) are ones whose *search* is too long; no margin reaches them.
- **The budget is 7 minutes, not 10** (NTF classic rule 3-6: 「マイクロマウスは7分間の持ち時間を有し、この間5回までの走行をすることができる」, with an explicit 5-minute variant for some contests). 10 minutes is the *other* event — マイクロマウス競技 (ex-half-size), 9 cm cells, up to 32×32. Everything else about this project matches classic (18 cm cells, 16×16, centre-2×2 goal), so read the classic rules, not the ones that come up first. Two more rules with teeth: **3-4 requires stopping ≥2 s in the start square before an automatic restart** (`RunManager.restart_dwell_s`, charged to the budget — not an optimisation target), and **3-5 makes a voluntary abort cost the entire map** (「それ以外の走行中止の申し出については、迷路に関する記憶をすべて消去することを条件に認める」) unless the fault is *obvious* to the chief judge. That last one is why a marginal safety abort is so expensive: a clean stop on a 0.09 red fraction may not read as 「あきらかに走行に異常」, and then the search is gone. By contrast rule 3-1 makes the record the *fastest single run* and the search run counts, so a speed run that runs out of time costs only the time.
- **The simulator's clock is `estimate_s` itself, so by default the estimate can never be wrong** (`sim.session.simulate_session`). That tests the *bookkeeping* (run counting, when to refuse a run) but says nothing about whether `time_margin` is enough. `actual_scale` is the knob that makes reality slower than the estimate; at the current 1.2 margin a 16×16 session stays inside the limit up to `actual_scale` 1.2 and simply runs fewer speed runs, which is the intended failure mode — past that the last run can overrun, which is the deal #87 deliberately took. Two related results worth keeping: on a realistic 16×16 the manager correctly declines to start a return+speed it cannot finish (search 260 s, estimate 412 s, margin 618 s > 340 s remaining — one run and stop), and the **turning mode does not fit a single speed run in the budget on that maze** (search 209 s and no speed run, vs 111.6 s search + 84.3 s speed turn-free). The 5×5 hardware gain of #76 was 2×; at 16×16 it is the difference between racing and not racing.
- **A generated maze is a quarter as hard as a real one, and matching the wall count does not fix it** (#84, `mazes/contest/`). Measured over 31 real All-Japan mazes (2010–2024) against 31 generated ones: interior walls 214 vs 193 — nearly the same — but the *solution* runs **59 cells vs 16**, the search **90 moves vs 21**, the speed run **77 s vs 25 s**, and the real mazes complete a median of **3 runs where generated ones always finish 5**. **Fourteen of the 31 fit no speed run at all in the 7 minutes** — the machine reaches the goal and never gets to race (that was measured before #89, #80 and the margin change; it is **3/31** now, see the `time_margin` bullet). Median runs used is 2 of 5, and exactly one maze allows all 5. Difficulty comes from where the walls are, not how many, and random generation cannot produce it at any density. But the *local* statistics do match (cells with no lateral wall 27 % vs 28 %, no longitudinal wall 28 % vs 30 %, cells with no wall at all 4 vs 5), so generated mazes are fine for exercising camera judgement and single-cell control (#85) and useless for exercising the search, the route planner, or the time budget.
- **Reading the neighbours buys stops, not distance — and the stop that a turn costs is not one of them** (#89, on by default, `--no-neighbors` to go back). At 960×720 the E/W neighbours' far walls (270 mm out) fall just inside the 281 mm half-frame, so one frame determines those cells completely and the mouse can cross them without stopping. Measured over the 31 contest mazes (medians, paired): **stops 90 → 73**, cells 90 → 93 in the earlier run but **−4 in the paired comparison** (the route does not get worse on average even though passed-through cells reveal nothing), search time −8 % at zero per-stop overhead and **−11 % at 0.5 s/stop**. 26 of the 31 improved, 4 got worse, 1 unchanged. Three things are worth knowing before re-deriving any of this:
  - **The issue's own estimate of 85 → 55 counted *observations*, not stops.** With the current primitives a direction change still costs a full stop (`CellMotion` decelerates to zero), and only same-direction cells merge into one motion. Counting "cells entered whose walls were already known" reproduces the issue's number exactly (85 → 52); the 21-stop gap between that and 73 is what **#80 (turning without stopping)** would unlock, not something a better wall reading can reach.
  - **`known` is now a bigger set than `visited`, and the speed run routes over it.** A cell whose four walls were seen from the outside is safe to race through; `RunManager._route` and `search_run`'s report pass `explorer.known` (formerly `visited`). On 16×16 that is 130 known cells against 87, and the number of contest mazes that fit a speed run inside 7 minutes went **17/31 → 23/31**. The speed-run time itself is a wash (median +0.00 s; 13 mazes faster, 8 slower).

- **A holonomic corner is *looser* than the straight corridor it connects, so rounding it costs no clearance** (#80, `motion/corner.py`). Turning means changing the translation axis, so a corner is just one axis decelerating while the other accelerates: start the next leg when the remaining distance hits the **blend distance `d = v²/2a`** and the old axis's own decel envelope `sqrt(2ad)` equals `v_max` exactly — the command is continuous across the seam, with no special case. At the tuned point (v 0.24, a 0.8) `d = 36 mm`, the path bulges `d/4 = 9 mm` toward the inside, and the machine passes **34 mm** from the inner post — against **21.4 mm** for the same machine going straight down a corridor. The bulge goes into the quadrant between the edge you came in through and the edge you leave by, and both of those are open by construction: there is no wall there, only one post. The tightest point of the whole route is still the broadside pass down the corridor, which happens whether you round the corner or not, so `min_post_clearance_m ≥ corridor_clearance_m` holds for every `d` up to half a cell. Three consequences:
  - **The speed dips, it does not peak.** Through the corner the velocity vector falls to `v/√2`, so the wheels never see a new speed peak; what rises is *acceleration*, since both axes change at once. `check_limits` already sized the ramp for exactly that case (both axes at max accel = 1665 step/s² against the L6470's 2000), so the corner was already inside the driver's budget before anything was written.
  - **`d` grows with the square of the speed**, so it is the knob that breaks first when the machine gets faster: at v = 0.6 m/s it is 225 mm, i.e. the machine would start sliding sideways while still in the *previous* cell's corridor, where the wall it is sliding toward is very much present. `check_limits` refuses that (`> pitch/2`).
  - **A 180° reversal cannot be rounded** — reversing a velocity means passing through zero — so `CellMotion` stops for it and starts the next leg cleanly. Same-axis legs simply merge into a longer one.
- **The corner blend is real: the model predicts the hardware to 0.6 % at the primitive level, and one corner is no less accurate than stopping** (#80). - **Fewest cells ≠ fastest, and a motion has a fixed cost of its own.** Measured over full turn-free sessions (#76, re-measured in #80, and both speeds re-measured on the 8×8 in #103). **At the current `v=0.30 m/s` with the #107 ramp (accel 0.7 / decel 0.6): 0.61 s per N/S cell, 0.60 s per E/W cell, plus 0.99 s per motion**; with the old 0.9/0.8 ramp the motion cost was 0.90 s, and at v=0.24 it was 0.77 / 0.75 / 0.825 — running cells together amortises the accel ramp, which is the whole point of `Leg(direction, cells)`. So `MoveCost` is `leg=1.62, cell_ew=0.98` (each ÷ the N/S cell time) and `RunManager.estimate_s` counts **N/S cells, E/W cells and motions separately**; with only cells the estimate came out low on a real route. The estimate reproduces the 8×8 speed run to **0.1 %** (20.00 s over 20 cells / 15 legs at `chain-legs 2` = 8 motions) and, with the 0.9/0.8 ramp, to 0.0 % (25.60 s at `chain-legs 1`) and, with the 0.24 constants, both #80 runs exactly (25.0 s stopping at every leg, 20.0 s chaining two — see `RunManager.motions`). **`leg` rose 1.10 → 1.48 and that is the interesting part**: cell time falls with speed but a motion's fixed cost *grows* (the ramp), so the faster the machine the harder the planner should work to use fewer legs — the two constants must move together, and with the speed. **The two speeds fit the trapezoid model**, so they can be interpolated: cell time scales as 1/v (0.77 → 0.61 = −21 % against 0.24/0.30 = 0.80), and the fixed cost grows by exactly the extra ramp `v/2·(1/accel + 1/decel)` (+0.071 s predicted, +0.08 / +0.07 s measured) — **everything else in it (0.55 s of stop + camera) is speed-independent, so never scale the whole thing by the speed ratio.** The N/S vs E/W gap is only 15 ms/cell — strafing needs 4 % more wheel speed (373 vs 358 step/s) but that still fits under `MAX_SPEED`, so the commanded speed is the same. The turning mode (#21, `--turn-in-place`) measures 0.75 s/cell + 0.36 s/leg + 1.76 s per 90° turn (180°: 2.52 s) + ~0.42 s of settle per primitive, hence `LEGACY_COST`'s `turn_cost = 2.9`. Re-measure all of these when the ramp limits or `CellMotionConfig` change — `speed_run` prints the per-axis fit at the end of every session.
- **The speed knobs live in one place** (`motion/tuning.py`, `add_tuning_args` / `build_tuning`). Speed, accel and KVAL have to be identical across `cell_move_demo`, `search_run` and `speed_run` or the numbers you tune in one don't apply to the others. The three layers are not independent, and `check_limits()` checks the couplings against the real kinematics — **run it before raising anything**: `CellMotionConfig`'s decel is clamped to the `RampLimits` ramp; the ramp must stay under the L6470 `ACC/DEC` register or the driver becomes the limit and stops overshoot; and the peak commanded wheel speed must stay under `MAX_SPEED` or it clips and the three-wheel speed ratio breaks (= the path curves). `L6470Profile.acc_steps_s2` is 2000 because the tuned ramp (0.9 m/s² + 8 rad/s²) peaked at ~1640 step/s²; the ramp is now 0.7 (#107) so there is more room than that.
- **Nothing slows down for a corner, and the two couplings that decides are `accel` vs `decel`** (#107, `RampLimits` now **0.7** and `CellMotionConfig.decel_mps2` **0.6**). `_command` uses one `v_max` for both the new primary axis and the old axis it is closing out, so a rounded corner (#80) is **entered and left at 100 % of `v_max`**; the velocity vector dips to ~76 % mid-corner purely because the two axes swap linearly, not as a deliberate slow-down. What rises is acceleration: both axes change at once, so the body sees `sqrt(accel² + decel²)` — and **that is independent of `v_max`**, which is why "the corner demands more at 0.30" was the wrong way to read it. Two things fall out, both measured on the 8×8:
  - **The corner acceleration was what aborted 1 run in 5.** At 0.9/0.8 it is 1.20 m/s² and the machine rotated at the corner exit until the 2.5° `--max-heading-residual` guard fired; the worst chained motion of a *completed* session was 2.37°, i.e. 95 % of the guard. At 0.7/0.6 (0.92 m/s²) the worst of 56 chained motions is **1.08°** with nothing over 1.5°, and the chained along-track residual's worst fell 9.0 → 2.0 mm. 0.6/0.6 (0.85 m/s²) measured the same on heading over 280 motions, so **0.92 is already enough** — but see the next point for why 0.6/0.6 is not the setting. The cost is the blend growing 56 → 75 mm (inner-post clearance 25.9 → 21.9 mm, still over the corridor's 21.4 mm) and the speed run 19.3 → 20.0 s (+4 %). **The middle of the distribution barely moves; what the change removes is the tail** — that is the signature to look for, since the failure was 1-in-5, not a general degradation.
  - **`decel` must be strictly below `accel`; equality costs 3 mm on every move.** The decel envelope `sqrt(2·decel·r)` demands *exactly* `decel` of deceleration, so an equal ramp leaves zero margin to follow it and the machine coasts past the tolerance band. Measured: 0.6/0.6 (0 % margin) overshoots a 1-cell move by **+3.00 mm** (140 hardware motions, range ±3.10, sitting just under `retry_pos_tol_m` = 4.0 mm so no retry fires and it simply stays there), against **+0.20 mm** at 0.7/0.6 (14 % margin) and +0.36 mm at the old 0.9/0.8 (11 %). The simulation reproduces it to 0.03 mm, so this is checkable off-Pi. **`check_limits` cannot catch it** — it only refuses `decel > accel`, and equality is legal to it. Keep ≥10 % margin. This one was in the hardware data of the first five sessions and was missed because only the *chained* residuals were being read; the single-leg motions are where it shows.
- **How the operating point was found** (#21, and how to redo it): raise one axis at a time, running `cell_move_demo --seq F4 --camera-pose --camera-yaw` at each rung and reading the time, the camera drift and the L6470 fault flags. Straight: 0.12/0.18/0.24/0.30 m/s gave 6.25/4.27/3.29/2.69 s over 4 cells (theory to 0.5 %), distance error ±2 mm up to 0.18 and −5 ± 4 mm at ≥0.24; 0.30 buys only 0.5 s per 4 cells over 0.24 and eats the `MAX_SPEED` margin, so **0.24 wins**. Turns: 1.5/2.0/2.5 rad/s gave 1.83/1.56/1.67 s, heading error (4 turns) −0.60/−0.36/−0.50°, so **2.0 wins** — 2.5 is not faster and is less accurate. No `STEP_LOSS`/`OCD` at any rung, so KVAL was never the limit; the limits here are slip and mechanical play, not torque. **"0.24 wins" was decided on the wrong scale, and 0.30 m/s is now the default** (#87 argued it, #103 measured both speeds and adopted it): 0.5 s per 4 cells is nothing per move, but over a whole 7-minute session it is the difference between **3 of the 30 contest mazes never getting to race and none of them** (total speed runs 38 → 54, median races per maze 1 → 2, simulated on the *measured* constants of both speeds at `chain-legs 2` — not on an assumed scaling). The two things #21 never tested were settled first. The peak commanded wheel speed at 0.30 is **453 step/s against the old `MAX_SPEED` 400, and it is the *lateral* case that clips** (forward stays under, which is why `--seq F4` looked fine), so `L6470Profile.max_speed_steps_s` went to **500** in the same change — `check_limits` catches exactly this, but note it **returns** its warnings rather than raising, so read the return value or a `try/except` will call 0.30/400 clean. And **since #76 half of every route is a strafe**, so the axis #21 never tested was the one that mattered — #87's aligned 4-cell strafes put 0.30 at least as accurate as 0.24 (mean |cross-track| 6.6 vs 8.2 mm). End to end on the 8×8 (#103, same day and pack, `--chain-legs 1`): search 33.2 → 31.2 s, speed run 27.6 → 25.6 s over four runs, zero L6470 faults, nothing aborted, identical map. **What it costs, both small and both known**: the corner blend grows with `v²` so 36 → 56 mm, taking the inner-post clearance 34 → 26 mm (still above the 21.4 mm the same machine has going straight down a corridor); and cross-track disturbance rejection weakens, because `v_cross_max` is a fixed 0.04 m/s and there is less time per cell — a simulated 10 mm kick leaves 2.6 mm instead of 2.0 mm. Raising `v_cross_max` to match has not been measured.
- **Every driving script polls `GetStatus` after each primitive** (`l6470.fault_flags`, `tuning.describe_faults`). GetStatus clears the flags on read, so a poll per primitive attributes `STEP_LOSS`/`OCD`/`TH_WRN` to the move that caused it. Note L6470 stall detection is BEMF-based and insensitive at low speed: **a flag means trouble, but no flag does not mean no slip**.
- **Stopping the machine is a signal problem, not a `finally` problem** (`motion/emergency_stop.py`). `with L6470Chain(...)` releases the coils on a clean exit, but `timeout`'s **SIGTERM** and some **SIGINT** paths skip it, and the L6470 then holds its last Run command — the machine spun until power was cut. Every driving script wraps the chain in `emergency_stop(chain)`, which releases (`soft_stop_all` → `hard_hiz_all`, in that order) *inside the signal handler* and then re-raises for the default action. **SIGKILL cannot be caught**: `python -m scripts.motor_stop` is the recovery, or cut VS. And **ESC does nothing** — these scripts read no keyboard; say Ctrl-C when telling someone how to stop.
- **Before moving, re-check that the path is clear** (`search_run --no-front-check` to disable). The planner only ever picks a direction the *map* says is open, so a wall appearing in the live frame means the **pose is wrong**, not the map. Aborting there is what keeps a pose error from becoming a series of collisions. Which body edge to look at now depends on the direction of travel, not the facing — `wall_detect.body_edge_for(direction, facing)`. **The check has its own, higher threshold** (`PATH_BLOCK_MIN_FRACTION = 0.20`) because it asks a different question from wall detection: detection has no prior and a miss is a collision (so 0.08), while the path check has a *strong prior that the path is open* and a false positive throws away a good run — one did, on a RIGHT reading of 0.09. Measured separation is 0.121 (no wall) vs 0.302 (wall), and the genuinely dangerous case (pose drifted, wall unseen) reads 0.00, so raising it costs almost no detection power. Same shape as `OFFSET_MIN_FRACTION`; keep the thresholds separate when tuning.
- **Two factors were each necessary and neither was sufficient, which is why changing one at a time said "nothing matters"** (#107). The 1-in-5 abort (`--max-heading-residual` firing on a rounded corner) survived a rubber trim, a full roller reshuffle, the ramp change and a W1 wheel swap when those were judged **one at a time by counting aborted sessions**. Counting aborts is a weak instrument: at a ~20 % session rate you need ~50 sessions per arm to see a 2× change, and ~20 sessions of it ordered nothing. **The per-motion residual tail is the instrument that works** — every chained motion is a sample, so one session is ~56 of them instead of one:

  | wheel + ramp | chained motions | median | **max** | >1.0° | aborts |
  |---|---|---|---|---|---|
  | old wheel, 0.9/0.8 | 12 | 0.88° | **25.68°** | 6 | 1 |
  | old wheel, 0.7/0.6 | 178 | 0.36° | **2.78°** | 2 | 1 |
  | **new wheel, 0.7/0.6** | 280 | 0.44° | **1.12°** | 1 | **0** |
  | new wheel, 0.9/0.8 | 73 | 0.50° | **5.43°** | 4 | 1 |
  | **new wheel, 0.7/0.6 — 25-run session** | **336** | 0.47° | **0.94°** | **0** | **0** |

  **Only the pair clears the tail**: 616 motions with one reading over 1.0° and no abort, against 263 motions with twelve and three for the other three cells. Softening the ramp alone still produced 2.78°; the new wheel alone still produced 5.43°. **A 2×2 read one factor at a time cannot see an interaction** — each row looked like "no effect" because the other factor was still broken. The medians say nothing (0.36–0.50° everywhere); it is entirely a tail effect, which is also why the middle of the distribution was no guide. What this does *not* establish is that the rate is zero, and it is not: **1986 chained motions have since produced exactly one abort** (#85), i.e. **0.050 % per motion** with a one-sided 95 % upper bound of 0.24 %, against 3 in 263 (1.14 %) for the configurations this replaced — a **23× improvement that is now an estimate rather than an absence**. Per session that is 4 % on the 8×8 and **6 % on a 16×16** (26 % if the true rate sits at the upper bound). The cause remains unidentified — it is not corner-specific either (a single straight leg produced +1.225°), and the one abort was a lateral event with the gyro and camera disagreeing in *sign* (see the contact bullet under #113).
- **An abort is recoverable in place, and the rule that looked like it forbade that applies to the *operator*, not the program** (#113, `localization/recovery.py`). When `--max-heading-residual` fires the machine is **already stopped** (the residual is judged after settling), so the camera is available. Rule 3-5's 「走行中止の申し出」 is a *human* request to the judge; a machine that re-establishes its own pose and drives on is not covered by it — at real contests a mouse that slips and recovers autonomously is fine, and the commentary treats recovering as a thing to credit. Beginners even build a straight edge into the chassis and push it against a wall to square up, which is legal (only hitting hard enough to break a wall risks disqualification). So **there is no return-to-start, no restart, and no run consumed** — fix the pose and continue. Three things make it work, and the third is the only hard one:
  - **Heading is exactly recoverable** (`median_axis_yaw` over ≥5 frames, σ≈0.1° at 960×720), because maze headings are always multiples of 90° so mod 90° is enough.
  - **Intra-cell position is recoverable to 2–3 mm** (`cell_offset`), but **only on axes that have a wall**.
  - **Which cell you are in is NOT recoverable from geometry** — the red bands repeat with the 180 mm pitch, so being one cell out looks identical. It is recovered from the **wall pattern** instead (`verify_cell`): compare the observed four edges against the learned map — **but only on the edges the map has actually observed** (`Explorer.observed`, threaded in as `known_edges`). `Maze` has no tri-state, so `has_wall` returning False means "no wall *or* never looked"; `flood_fill` may read that optimistically because it is going to go and look, and a *verifier* may not. Getting this wrong is not subtle — the first hardware run **stopped on the second move of the search** reporting "lost", because during a search almost every edge is unobserved and so every comparison fails. CLAUDE.md already said it ("the `known` set is what carries 'unknown', so any new consumer has to thread it through") and the new consumer did not. During the search the verdict is therefore usually *unverifiable* rather than *contradicted*, and the two must not be merged: unverifiable falls back to a different piece of evidence — the **along-track residual**, which excludes a whole-cell slip if it is under 30 mm (`CELL_SLIP_MAX_M`; the three recorded aborts were 10–14 mm, so a whole-cell slip has never actually been seen). It does not need to be globally unique, only to separate the believed cell from its **±1 neighbours along the travel axis**, which is the only error a distance slip can make. The believed cell wins when it matches (the prior is strong); a neighbour is taken only when the believed cell fails and exactly one neighbour matches. Zero matches means lost, two means indistinguishable — **both refuse**, and the honest failure case is two featureless neighbours (a wall perpendicular to the travel axis is not shared sideways, so E/W travel cannot use N/S walls to separate candidates).
  - **The guards invert in recovery mode, and that is the whole design.** `MAX_HEADING_CORRECTION_RAD` is 5° because *during a healthy run* a larger reading is a mis-measurement. In recovery we already know the pose is wrong, so the correction is allowed to 20° (`RECOVERY_MAX_HEADING_RAD`) and the gate moves to **measurement quality** instead — the frame-to-frame yaw spread must stay under **1.5°** (`RECOVERY_MAX_YAW_SPREAD_RAD`). Same asymmetry as the path check's 0.20 against detection's 0.08: **never reuse a number under a different prior.** Two corrections to that gate, both earned on the first hardware run: **0.5° was taken from #88's 0.11–0.26° and that figure was measured with the machine parked in one cell**, whereas in a run the stopping position varies and cells with fewer walls give shorter, fewer segments — 14 real recoveries spread **0.08–0.45°** and the 15th read 1.03° and ended the session. And **spread is a weak guard in the first place**: the dangerous failure is a *confident* wrong reading, which spread cannot see — the `axis_yaw` mis-read that applied a **−13.27° "correction"** and the red ruler bag's steady +5.4…+7.4° (#89) both had small spread. What actually protects the run is the 20° cap (bounding the damage), the **wall-pattern check** (independent evidence — the wall ROIs are position-based, so a yaw error does not corrupt them) and the **path check on the next move**. Tightening the spread gate does not stop the dangerous case; it only refuses healthy recoveries. The recovery log therefore prints segment count and total length, because without them a large-spread event cannot afterwards be told apart from "a cell with few walls".
  - **A jammed machine cannot read its own cell, and the two numbers that decide it are nearly equal** (#85, `perception/lattice.py`, `recovery.wall_contact`). The first real jam: the machine ended in (6,6) **28 mm east of centre with the rear-right wheel against the east wall**, rotated **−5.07°** (camera, 5-frame spread 0.18°). The ROI search is **±40 px = ±23.5 mm**, so at 28 mm the bands were out of range, the FRONT ROI picked up a post, and the read came out `{N, E}` against a true `{E}` — `verify_cell` compared that against (6,6) and its two neighbours, matched none, and correctly said "lost". **The corridor clearance is 21.4 mm and the ROI search is 23.5 mm**, i.e. *the machine cannot lose its bands without also being at risk of touching a wall*. So the fix has to be a pair: measure the offset a way that does not depend on the ROIs, **and** refuse to drive on when that offset exceeds the clearance on a side that has a wall. Do one without the other and you get a machine that knows exactly which cell it is in and drives on with a wheel against a wall.
    - **Widening the ROI search does not help** — replayed on the jam frame at 40 / 60 / 80 / 100 / 120 px the four readings never moved (0.12 / 0.00 / 0.00 / 0.22). The wall it is touching is **occluded by the machine itself**; only the middle rows of the frame see it. More search range cannot find red that is not in the picture.
    - **The lattice phase does work, because it uses every red pixel instead of four boxes.** Walls and posts only ever sit on the 180 mm lattice, so the weighted circular mean of the red mass at the lattice frequency gives the offset mod 180 mm, folded into (−90, +90] because the machine is inside a cell. On the jam frame it returned **−27.9 mm** laterally against a hand-measured −28.0, and −3.4 mm fore-aft against −6.0. Two things are required and both were found by it failing first: **de-rotate by the measured yaw** (at 5° one wall moves 60 px across the frame and the 306 px period smears — the fore-aft reading went −17.3 → −3.4 mm), and **separate vertical from horizontal structure before profiling** (a wall spans exactly one pitch on the perpendicular axis, so it adds nothing but denominator and crushed the fore-aft confidence below the threshold — that axis read "unmeasurable" until the split). Posts belong to *both* profiles, since a post sits on both lines.
    - **The wall was not moved, and proving that needs a reference other than the wall itself.** Using the two posts on the west lattice line (−119 mm) and the outer wall to the east (+243 mm) — neither of them the one being touched — the machine is +28 mm east; the touched wall then sits at **+92 mm from the cell centre against a nominal 90**. So the maze did not need rebuilding. Reading the offset off the contacted wall would have been circular and would have proved nothing.
    - **The gyro and the camera disagreed in *sign***: the estimator's residual was **+5.30°** (CCW) and the machine is physically at **−5.07°** (CW). That is a third pattern — #81's sampling error makes the *point sample* the outlier while the continuous integral tracks the camera, and #103's rub puts both gyro numbers off *together in the same direction*. The along-track residual was normal (0.3 mm; #85's earlier post graze was 6.3 mm) and the cross-track was **9.3 mm against a normal 0.2–1.8**, so this was a lateral event. The contact direction is at least self-consistent: a reaction pointing west applied *behind* the centre of mass gives `τ_z = r_x·F_y < 0`, i.e. the clockwise rotation observed. **What cannot be decided from this data is the order of events** — whether it rotated CCW and was slammed back, or the gyro integrated something that never happened.
    - **This is the first guard trip since the #107 pairing, and it converts a bound into an estimate**: 1122 chained motions with 1 abort = **0.089 % per motion**, against 3 in 263 (1.1 %) for the configurations #107 rejected. The pairing is ~13× better and **not zero**, which is exactly what #107 said its zero-abort run could not establish.
  - **`axis_yaw` is mod 90°, so a big rotation is a trap, not a harder problem.** At 50° it confidently reads −40° and snaps to the wrong lattice, then drives straight at a wall. `RECOVERY_ABANDON_RAD` refuses above **30°**. The three recorded aborts (2.78 / 5.43 / 25.68°) are all inside it, but 25.68° has only 4.3° of margin. The BNO055's magnetometer could in principle resolve the fold, but three permanent-magnet steppers sit next to the IMU and their field moves with rotor position — and at 30° the free-standing walls are down and the run is over anyway, so it is not worth building.
  - **Recovery is capped at once per session** (`--max-recoveries`, default 1). A machine whose fault is not understood and keeps recurring is more dangerous to keep running than to stop. `--no-recover` restores the old behaviour. Recovery makes an unexplained failure cheap instead of waiting to explain it — and that was the right call even though the failure then turned out to be reachable: see the next bullet.
- **Never let a wall *observation* clear a wall the map already knows** (`strategy/explorer.py`). Two safety valves, both earned on hardware: (1) **outer walls are read-only** — the first real `search_run --dry-run` had the camera call the boundary behind the robot "no wall" and erase it from the map; (2) `sticky_walls` (default) keeps an already-seen wall when a later look says "absent", counting it in `Explorer.conflicts` instead. A false negative drives the machine into a wall; a false positive only costs a detour, so the asymmetry is deliberate. A rising `conflicts` means pose error or mis-detection, not a maze that changed.
- **Camera-measured position is the only absolute fix for translation** (#54, `perception/cell_pose.py`). Walls sit exactly 90 mm from the cell centre, so *how far a red band has moved from its calibrated place* is the machine's intra-cell offset: `offset_px / px_per_mm`, with `px_per_mm` self-calibrated from `CALIBRATED_BANDS` (opposite bands are one 180 mm pitch apart). `best_roi_red_fraction` already returns that offset as a by-product of the band search. Two rules: **only correct the axes you measured** (an axis with no wall has no band — treating it as 0 drags the machine toward the centre on evidence you don't have), and reject corrections beyond `max_error` (50 mm) as mis-measurements. On hardware the measured offsets stayed ≤18 mm over a 6-move run instead of growing; a **systematic ~6 mm body-fixed bias** remains (all 7 lateral readings negative, mixed signs in world terms → a camera-mount offset, or `CALIBRATED_BANDS` taken while the machine itself sat a few mm off). Null it by measuring with the machine ruler-centred, then shifting `CALIBRATED_BANDS`.
- **The band search saturates at the frame edge, and a saturated reading looks like a small honest offset** (#21). `best_roi_red_fraction` slides the ROI ±40 px but skips positions that would fall outside the image, so the BACK ROI (`y=417`, height 38, frame 480) can only travel **+25 px = +14.7 mm** downward. Drive forward past that and the reading pins at the limit instead of growing: a ruler-measured 20 mm move produced a 7 mm reading. `apply_cell_offset` then believes the machine is nearer the centre than it is. The measurement is otherwise excellent — frame-to-frame spread 0.0 mm, LEFT vs RIGHT agree to 1.2 mm, FRONT vs BACK to 1.5 mm — so the fix is to **detect and drop**, not to distrust: `best_roi_red_fraction` returns a saturated flag and `cell_offset` discards that edge (wall presence still uses the fraction). Forward offsets beyond ~15 mm simply cannot be read from the BACK wall; the wall top leaves the field of view.
- **Comparing two motions without `--align` measures how you put the machine down, not the motion** (#87, `cell_move_demo`). A strafe travels along the *body* axis, so a placement tilt θ lands as `D·sin θ` of cross-track: over 4 cells that is **12.6 mm per degree**, and the corridor only allows 21.4 mm per side. Eight runs comparing 0.24 against 0.30 m/s were spent before this was noticed — the tilt varied from −0.96° to +1.65° across them, and the tilt alone predicts the measured cross-track to within 7 mm on 6 of the 8. Adding `--align` (which does what `apply_axis_heading` does at every stop of a real run) collapsed the spread from **37.1 mm to 18.8 mm**, and the two 0.30 runs — the wild ones, spreading 18 and 36 mm — came back to +3.5 and −11.2. **The tilt warning used to fire only when `--align` was given**, i.e. it was silent in exactly the case where it bites; it now fires whenever the yaw is measured and prints the mm it will cost.
  - **The machine really does rotate when the coils energise, by up to 1.7°, in either direction.** Measured by reading the axis yaw with the motors in HiZ (`wall_detect --measure`) and again seconds later from `cell_move_demo`'s post-energize `before` reading, same cell, same exposure: +1.67°, +1.14°, −0.89°, −0.75° on four of seven pairs, with the position moving ≤0.6 mm (a hand-nudge would move the position too). #72 had this at +2.06° and took it to −0.03 ± 0.26° by tightening the front wheel's hub screw; the joints were checked again this time and found tight, so **the cause is not the same one**. It needs no emergency action — every driving script energises before its first camera reading, and `apply_axis_heading` nulls it at every stop — but it is why a *demo* without `--align` cannot be compared against anything.
  - **Raising the speed does not cost cross-track accuracy — 0.30 m/s is if anything better.** Two rounds of aligned 4-cell strafes on the black floor, cross-track in mm:

    | | left | right | mean \|drift\| |
    |---|---|---|---|
    | 0.24 m/s | −2.4, −7.1 | −15.3, −8.2 | **8.2** |
    | **0.30 m/s** | +3.5, +5.9 | −11.2, −5.9 | **6.6** |

    **Three of the four paired comparisons favour 0.30** and the fourth is a 1.1 mm difference at the resolution limit. Times 3.37 s and 2.82 s (the model to 2 %), no L6470 faults at either, heading residual ≤0.89°, gyro-vs-camera 0.026–0.710°. `check_limits` passes at `--v 0.30 --max-speed 500`, and the corner blend grows 36 → 56 mm with the inner-post clearance 34 → **26 mm**, still above the 21 mm the same machine has going straight down a corridor. **Nothing in the motion argues for staying at 0.24.** What adopting it needs is not more evidence but a re-measurement: `cell_time_s` / `straight_time_s` / `MoveCost` were all fitted at 0.24 and `RunManager` would otherwise budget the session wrongly — which is precisely the failure #87 just removed.
  - **The forward crab could not be measured, and chasing it is not worth it.** Four aligned `F4`/`B4` runs (machine turned 90° so it drives along the same corridor — the crab is a body-frame property, `axis_yaw` is mod 90°, and this puts the cross-track on the strong LEFT/RIGHT bands instead of the weak BACK) gave cross-track **+0.0 and −19.3 mm on the two forward runs**, whose placement tilts (−0.36°, +0.11°) and in-run rotations (+0.42°, +0.09°) were both negligible and nearly identical. **There is no explanatory variable for a 19 mm spread.** The −19.3 mm run also fell **27 mm short along-track** while its odometry residual was 0.4 mm, and that pair was read as a **graze**. **It was not one** — see the audible-rub bullet below: the operator was watching and nothing touched a wall, and the cause turned out to be the competition floor *board* flexing up against the chassis underside. So the "4-cell move in a 1-cell corridor is near the clearance limit" lesson does **not** rest on this run; a real run still corrects every 1–2 cells for other reasons. What survives untouched is the measurement this sub-bullet is actually about: there is no explanatory variable for the 19 mm cross-track spread, and the crab's payoff over that interval is **1.3–2.5 mm**, inside the noise of everything else. Combined with the lateral −0.40 ± 0.14° overlapping #17's converged −0.22 ± 0.17°, there may be nothing to fix at all. **Do not spend runs on this before the time constants.**
  - **A direction-dependent bias survives alignment and is not about speed**: over all 8 aligned runs, left moves land at **−0.0 mm** and right moves at **−10.2 mm**, i.e. a constant −5.1 mm plus a term that flips with direction worth −5.1 mm (**a crab of −0.40°**, against the −0.22 ± 0.17° #17 converged on with *forward* runs). 10 mm of the 21.4 mm corridor margin on a 4-cell strafe; a run corrects every 1–2 cells so it is not immediately dangerous, but it is the next thing to chase.
- **The camera and a ruler agree to 2–3 mm; use the camera** (`cell_move_demo --camera-pose`). Measuring travel before/after a move with `cell_offset` and differencing in the ideal-grid frame matched a tape measure at every rung of the speed ladder (722/720/721/710 mm vs +2.4/0.0/−1.2/−8.2 mm). One 703 mm ruler reading that disagreed by 15 mm sent us chasing a phantom for an hour — **repeat a surprising measurement before theorising about it**. Note the axes it prints are the body axes of the *starting* pose, not maze north/east: this script's estimator starts at φ=0, which is wherever the machine was placed.
- **Energize before you measure the starting pose** (`VelocityDriver.energize`). The L6470 sits in HiZ after reset and only energises on the first motion command, at which point each rotor snaps to its nearest detent and the chassis jumps. Measured at **+2.06°** — though most of that turned out to be a loose hub screw (below); with the joints tight it is `−0.03 ± 0.26°`, i.e. the detent snap alone is under the measurement noise. Measure first and that jump is misfiled as "rotation during the move", which is exactly what made the gyro and the camera disagree by up to 1.6° on pure straights. Every driving script now issues a zero-velocity command and settles before the first camera reading.
- **A loose fastener will masquerade as an irreducible mechanical limit — check the joints before you design around one** (#72). A `+2.06°` chassis jump on energize, a 0.9–1.45° residual at the end of every turn, and ±1.2° of scatter in the crab estimate all fitted the arithmetic for the omni wheel's roller clearance (rollers have 0.5–1.0 mm of slop along the wheel's rotation direction; the contact point is `center_to_wheel_m` = 45.07 mm from the centre, so the chassis can rotate **θ = play / 45.07 mm = 0.64–1.27°** with the wheels held still). The fit was good and the conclusion — "inherent to the wheel, you cannot control your way through it" — was wrong. **The front wheel's hex hub screw was loose.** After tightening it the energize jump went to `−0.03 ± 0.26°` (5-frame means; consistent with zero), while the turn residual and overshoot did *not* change — proving those were never play (see #73). This wheel takes a separately-sold hub through a hex socket, so there are three joints in series before the rollers (shaft↔hub, hub↔wheel, roller↔plate); measure them separately by holding a different part each time. **W0's spoke angle is ~0°, i.e. it drives purely sideways** (`body_to_wheels(0,1,0)` ≈ 1.0 for W0), so slop there lands directly on the lateral axis — which is why the crab calibration would not converge until it was fixed (scatter 1.2° → 0.05°). **But the rollers were not innocent** — see the next bullet (#103): they *bind* as well as wobble, and the play arithmetic above only covers the wobble.
- **The omni wheel's rollers have rubber longer than their cores, and it fouls the wheel plate — direction-dependently** (#103). The rollers are over-moulded (plastic core, rubber surface) and in places the rubber stood proud of the core; pushed axially, that lip touches the wheel plate and resists rotation. A roller is pushed axially exactly when its wheel is **skewed to the direction of travel**, and the *side* it is pushed toward follows the sign of the cross-track component — so an overhang on one side of one roller produces friction that depends on which way the machine is going. That is the shape #103 could not explain: all four rounded corners demand the same wheel speeds to within 1 % (peak 0.230–0.233 m/s), yet only **S→E** ever aborted, at a consistent **+1.3° of uncommanded rotation against the 2.5° guard**. **The requirement was symmetric; the resistance was not.** Four things worth keeping:
  - **It was found by ear, and the reasoning that got there is reusable.** Forward and backward drive the *same* two wheels at the *same* speeds (W1 355 / W2 344 step/s, sign flipped — `body_to_wheels` confirms it), so a noise present in only one direction **cannot** be torque, KVAL, current or supply, and must be mechanical. `cell_move_demo --seq F4` against `--seq B4` is the whole experiment; it took an hour of listening and no instrument.
  - **The bench test is to push a roller to one side by hand and turn it** — that reproduces a skewed wheel on the desk. Several wheels were then plainly stiff. Trimming the proud rubber cut the noise sharply and shrank the drift when it did occur.
  - **This partly reverses #72.** #72 fitted the same class of symptom to roller *clearance*, found a loose hub screw instead, and wrote the rollers off. The rollers were involved after all — by **binding, not slop**. A roller has two independent failure modes and `play / 45.07 mm` only covers one; **"we already ruled the rollers out" was ruling out one mechanism, not the part.**
  - **The noise is fixed; the rotation is a different fault that was riding along with it** (#107). Two trims later the rub is **audibly gone entirely**, and the direction-dependent rotation is exactly where it started: measured as `(B,D − F,A)/2` over four points — **0.83° → 0.62° → 0.86° → 0.92°** — it survived a coupling re-seat, the 0.24 → 0.30 m/s change, two rubber trims, and **a full removal and reshuffle of every roller** (orientations and positions deliberately not reproduced). **Shuffle the rollers and it does not move, so the rollers are not making it.** (Caveat: widespread residual overhang would also survive a reshuffle in aggregate — but paired with the noise being gone, "two faults, not one" is the natural reading.) **And it matters less than the chase implied**: 0.9° is 180 mm × sin 0.9° = **2.8 mm** of cross-track on the following leg, it is well under the 2.5° abort guard, and `apply_axis_heading` clears it at every stop — so it is *not* a candidate for "grazes a wall once every few sessions". **#103's pair was a good metric for the question #103 asked** (does the run abort?) **and the wrong one for #107's** (does it graze?); carrying it over was the mistake. Judge the trimming by the bench test — push a roller sideways and turn it — and judge the outcome by a full 8×8 session. If 0.9° is ever chased on its own, the discriminating run is **single legs with no `--chain`** in all four directions: antisymmetric across opposite directions points at wheel geometry (`wheel_diameters_m` has W0 at +1.5 % and was only ever calibrated from forward runs), present only when chained points at the blend.
- **An audible rub has had four different causes, and on the one chased hardest the first two guesses were both wrong** (#87 / `fed30ba` / #80 / #103). The symptom is identical every time: a scraping noise during a run, sometimes with distance missing, and **nothing whatsoever in the log** — no L6470 fault (BEMF stall detection is insensitive at this speed) and an odometry residual of 0.4–0.5 mm, because odometry integrates *commanded* speeds. The noise is the only live signal and it does not say what is rubbing, so the causes are collected here rather than each under its own subsystem:

  | cause | what rubs | the tell |
  |---|---|---|
  | **Floor board on the chassis underside** (#87, fixed in `fed30ba`) | the competition floor is a *board* and it flexes; at 0.30 m/s the machine shakes enough for it to touch | cost **27 mm along-track** on one 4-cell move. Pack was **full at 12.17 V** and the operator saw no wall contact — both guesses excluded. Fixed by lowering the battery (less shake) and adding spacers (less flex) |
  | **Roller rubber on the wheel plate** (#103, #107) | rubber standing proud of the roller core, once the roller is loaded axially | **direction-dependent**: audible going backward, silent going forward at the same wheel speeds. Bench test — push a roller sideways by hand and turn it |
  | **A run-down pack slipping** (#80) | the wheels, on the floor | only at low state of charge. Check the **LEDs** before a session; the 12 V rail is regulated so a voltmeter cannot tell you (`docs/venue-checklist.md`) |
  | **Actually grazing a wall** | the chassis, on a wall | along-track short *and* cross-track drift. On a socketed floor the wall does not topple, so watch the machine, not the maze |

  **The discrimination that works is not the table, it is one A/B**: `cell_move_demo --seq F4` against `--seq B4`. Forward and backward drive the *same* two wheels at the *same* speeds (W1 355 / W2 344 step/s, sign flipped), so anything appearing in only one direction is mechanical and **cannot** be supply, current, KVAL or torque. That is what found #103, by ear, in an hour. After that: full LEDs rules out the pack; an operator watching rules out a graze; happening on the black board but not the wood floor points at the board. **What you must not do is reason from "we have heard this noise before"** — the 27 mm event was called a graze, then a flat pack, before it turned out to be the floor board, and #103 was a fourth thing again. **Three of those four diagnoses were written down as fact at the time.**
- **The turn overshoot is a lag, but not the one #81 fixed — turns and translations fail for different reasons** (#73, `CellMotionConfig.gyro_delay_s`). Fixing the gyro sampling (#81) changed the turn overshoot not at all: measured after it, `Q,Q,Q,Q` at ω = 2.0 rad/s overshoots **4.5°** against 2.3–3.2° before. The single-run A/B says why — during a turn the point sample and the continuous integral agree to **0.2°** (against 1.32° in a translation), because a turn's rate is large and slowly varying, so there is nothing fast to alias. **The two issues were never the same root cause.**
  - **The overshoot is `≈ 1.5° + 26 ms × ω`, not proportional.** Measured: 4.5° at ω = 2.0 / dt = 20 ms, 3.75° at ω = 2.0 / dt = 10 ms, 3.03° at ω = 1.0 / dt = 20 ms. Halving ω does not halve the overshoot, so there is a fixed part the lead compensation cannot touch.
  - **The mechanism is that the lag shifts the whole decel schedule, not just the final test.** Simulating a lagged gyro: when the *estimated* remaining crosses zero the machine is still turning at 39 °/s, because the envelope has been computing `sqrt(2·a·r)` on a too-large `r` the whole way down and the ramp cannot make up the difference. That is why the overshoot scales with `ω_max` rather than with the rate at the moment of termination.
  - **`--dt 0.01` speeds turns up by 0.29 s (1.83 → 1.55 s), and it is entirely a retry effect.** The finer tick makes the overshoot smaller (4.5 → 3.75°), which shortens the retry. Translations are *completely* insensitive to `dt` (1 cell 1.12 → 1.13 s, 4 cells 3.36 → 3.38 s, simulated) because they never retry. Do not reach for a faster control loop expecting a general speed-up.
  - **`gyro_delay_s = 0.026` is the fitted delay and it lands where the model says.** It subtracts `delay × measured rate` from the turn's remaining (a first-order lead inverting a first-order lag), in both the termination test and the decel envelope. Measured on hardware: **1.83 → 1.42 s per turn (−22 %), retries 4/4 → 2/4, overshoot 4.5° → 1.83/1.96°** — exactly the 1.5° fixed part the fit predicted would survive. The residual also stopped being *biased*: before, all four turns ended +1.5° short, so the error accumulated; after, they land ±0.9° with mixed signs. **Fit it from two ω values, never one** — with a fixed part in the sum, a single point gives the wrong delay, and too much lead stops the turn short.
  - **The surviving 1.5° is the ramp-down after the decision.** At the moment the (compensated) remaining crosses the tolerance the machine is still turning 20–39 °/s, and bringing that to zero at the 8 rad/s² ramp costs about a degree. No amount of lead removes it; it would take a gentler envelope tail.
  - **The payoff is small and that is the point.** Since #76 the machine does not turn while running; turns survive only as the `gyro_scale_z` calibration procedure and as an escape route. This was worth finishing because that calibration is the only way to measure the gyro — not because a competition run gets faster.
- **The "invisible rotation" was the control loop point-sampling a gyro that updates twice as often** (#81, `hal/gyro_sampler.py`). The BNO055 in NDOF mode outputs at **100 Hz**; the 50 Hz control loop read `imu.gyro[2]` once per tick and treated that one number as the average rate for the whole 20 ms — **throwing away half the chip's output**. Within a single tick the rate actually swings by a median of **5.4 °/s and up to 35 °/s**, so the point sample was a lottery, and it did not average out. Measured **in one run** (the estimator fed by continuous integration, the old point sample accumulated alongside for comparison, so no run-to-run variation): camera **−1.153°**, continuous integral **−1.161° (0.009° off)**, point sample **−2.476° (1.323° off)**. That 1.32° is the same size as the 1.154° that #80's chained run showed, and the lateral position error in the same pair went **−14.1 mm → −0.6 mm**. The fix is to sample on a thread faster than the chip updates and integrate `rate · dt` (over-sampling is harmless — the chip holds its value, so integrating duplicates reproduces the zero-order hold exactly). Three things worth keeping:
  - **A gyro-vs-camera disagreement is not always sampling — a mechanical rub produces one the same size, and the tell is which gyro number is wrong** (#103 / #107, measured 2026-09-12). On a `B,D --chain` run that rubbed audibly: camera **+0.834°**, continuous integral **+1.941°**, point sample **+2.240°**. **Both** gyro figures are off together, and that is the discriminator — when the cause really is sampling, the point sample is the outlier and the continuous integral tracks the camera (#81's own run: camera −1.153, integral −1.161, point −2.476). Here the BNO055 is rectifying vibration that is faster than its own 100 Hz output, so **sampling harder on our side cannot reach it**. The physical rotation was *normal*: +0.834° against +0.822 / +0.899° on the two clean runs of the same pair. What the rub cost was **1.1° of rotation the estimator believes but the machine never did** — `apply_axis_heading` nulls that at the next stop, but inside a chained chunk it steers the remaining legs — **and, on the axis it travelled, a 15.9 mm disagreement between the camera and the odometry**: the camera says it went **8.2 mm too far**, the odometry believes it stopped **7.7 mm short**, against 1.0–4.0 mm of camera-vs-odometry disagreement on the five clean runs of the same session. Two notes on that pair. **They were first written down here as *agreeing*, because both are about 8 mm** — they have opposite signs, and the only way to see it is to refer each to the direction of travel (the script's own `前後 +` label means "overshot" only for a *forward* move, so a backward leg reads inverted). And **the disagreement, not the distance, is the signature**: losing distance on a chained leg is ordinary — over the same session *every* measurable run came up 2.3–11.7 mm short on its **second** leg while the odometry read 0.4 mm, which is #80's 3.5–5 mm per corner and has nothing to do with rubbing. The caveats do not reach 15.9 mm either: this run had the session's largest heading error (1.98°), worth 180 mm × sin 2° = 6.3 mm of coupling between the axes, and the camera itself resolves 2–3 mm. **`GyroSampler`'s within-tick spread looked like a vibration sensor and is not one — that claim was made on one session and died on the next.** In this session the *max* separated **B,D 46.0–56.5 °/s from F,A 21.0–31.8 °/s with no overlap**, which read as "it flags the two B,D runs that were not audible". The next session, after the rubber was trimmed again, **the rub was audibly gone entirely and the spread did not move** (B,D 30.9–57.2, F,A 31.2–41.4, overlapping) — so the 30–57 °/s band is the machine's *baseline* vibration through a rounded corner at 0.30 m/s, not the rub. Worse, the separation vanished because **F,A rose** (mean 27.2 → 36.4) about as much as B,D fell (50.0 → 42.1), which no "the rub got better" story explains. The reading is still printed by every driving script and is worth a glance, but **do not treat it as a rub detector**: one session of n=3 either side was not enough to call a clean 2× separation a metric.
  - **The error grows with the rotation, not with time.** #80's pair already ruled out a constant rate bias: the chained run had *less* motion time (3.31 s vs 4.50 s) and *more* error. A sampling artefact tied to what the machine is doing fits; a drifting zero does not.
  - **A dead sampler must be loud.** If the thread stops (I2C error) and the API keeps returning 0, the run reads it as "not rotating" and drives on while the heading quietly rots. `GyroSampler.error` is checked in the driving scripts, which abort.
  - **Drain the accumulator before each motion.** The integral keeps running while the camera work happens between moves, so the first `take()` of a motion would otherwise cover several seconds; multiplying that average by one 20 ms tick dilutes the rotation. Every driving script calls `drain_gyro()` before a primitive.
- **Fusion policy** (`localization/`): translation comes from wheel odometry, **heading from the gyro** (`update_with_gyro*`, since slip hits rotation hardest), and absolute drift is pulled in by the two camera corrections below. Prefer this split over trusting wheel-derived dφ.
- **The gyro's heading reference is the machine's pose at *start-up*, not the maze.** `CellMotion` holds the ideal-lattice heading in the estimator's frame, but that frame rotates relative to the maze as each move leaves 0.3–0.5° behind. Nothing bounded it until `apply_axis_heading` (`localization/grid.py`): at every cell stop, `axis_yaw` gives the heading relative to the maze axes (mod 90°, which is exact because maze headings are always multiples of 90°), and the estimate is snapped to that lattice. Without it the machine crabs a fraction of a degree per run, which compounds — on hardware it drifted 10 mm per 4 cells and eventually shoved a wall aside. Position correction (#54) alone cannot catch this: it re-centres the machine but leaves it pointing wrong. **The guard on that correction has to be tight** (`MAX_HEADING_CORRECTION_RAD = 5°`): at 15° a single bad `axis_yaw` reading applied a −13.27° "correction" and destroyed the run. Real per-move drift is 0.3–0.5°, so anything past a few degrees is a mis-measurement, not a pose error. `search_run --max-heading-residual` (2.5°) additionally aborts when the residual after a move stays large — the correction refusing to converge is the earliest sign that the machine has lost the maze.
- **A crab (translation ≠ heading) means `wheel_angles_deg` no longer matches the hardware — but you must subtract how the machine was *placed* first, and you cannot resolve better than ~0.25° per run.** A uniform spoke-angle error δ turns a pure `vx` command into `vy = vx·sin δ` (derivation: `d_i(θ+δ) = R_δ d_i(θ)`, so the body velocity is the commanded one rotated by δ). The lateral drift you measure is `720 mm · sin(placement tilt + rotation during the run/2 + δ)`, so always run with `--camera-yaw`: the `before` axis angle is the placement tilt and the camera before/after difference is the rotation during the run. #17 read the whole thing as δ and over-corrected. **Each measurement carries σ≈0.24°** (axis-yaw median σ=0.20° plus half the run rotation), so average ≥2 runs — and note that a tight-looking pair is luck, not precision: three config points gave spreads of 0.046 / 0.015 / 0.723°. Converged at `[0,120,240] − 1.49°` with δ = −0.22 ± 0.17°, i.e. nulled to the noise floor. The response slope between config points measured −1.46 rather than the theoretical −1, so the three spoke errors are probably not a uniform rotation; extrapolate from two measured points rather than applying the raw δ. **This will not converge at all while any hub screw is loose** (#72) — the scatter was 1.2° before the front wheel's hex screw was tightened and 0.05° after.

- **Forward and sideways are driven by different wheels, so they have different scale errors** (#76). The IK coefficients for `vx` are `W0 +0.026 / W1 −0.879 / W2 +0.853` and for `vy` are `W0 +1.000 / W1 −0.477 / W2 −0.522`: **W0's spoke angle is ~0°, so it is effectively a lateral-only wheel** and barely turns during a straight. Every `wheel_diameter_m` calibration to date used forward runs, so it is really *W1/W2's* diameter and says nothing about W0 — and a unit test can never catch this, because odometry integrates the *commanded* speeds. Measured on a 1×15 corridor with the same floor, walls and distance, changing only how the machine was placed: forward 720/723 mm and 1435/1440 mm (+0.02 %), strafe 718/731/728/734/725 mm (**+1.00 %**). A W0 circumference +1.5 % explains both at once, so `robot.yaml` grew `wheel_diameters_m: [d0, d1, d2]` (`RobotConfig.wheel_circumference(wheel)` → `KiwiKinematics.wheel_speed_to_step_hz(v, wheel)`, consumed in `VelocityDriver._command`). Scaling the *distance command* instead would not work — W0 also holds cross-track during a straight.
- **Config values are calibrated, not nominal**: `wheel_diameter_m` (~0.0473, effective ≠ nominal 48 mm) and `center_to_wheel_m` (~0.0451) started from `scripts/calibrate.py` (#11) and were re-fitted **on the maze floor** in #17; `gyro_scale_z` (~0.984) came from the camera check below. Don't "fix" them back to spec values, and don't hard-code them in tests — read them off `RobotConfig` (see `tests/test_smoke.py`).
- **Re-fitting `wheel_diameter_m` must scale `center_to_wheel_m` by the same factor.** Only the ratio `L / d` sets the commanded ω, and `calibrate --rotate` derived `L` under the *then-current* `d`; changing `d` alone silently rescales every rotation command. (Turn *accuracy* doesn't depend on either, since heading closes on the gyro — but the commanded ω would no longer mean what it says.) Method used in #17, on the maze: run `--seq F,F`, measure the machine's offset from the end cell's centre as **(front wall gap − back wall gap) / 2** (no need to know the chassis dimensions), then `d ← d · actual / odometry`. Two passes took 2 cells from +7 mm to <1 mm (0.04629 → 0.04732 → 0.04771). Note the maze floor is interlocking panels, so the *true* pitch isn't exactly 180 mm (one cell here is ~1 mm oversized) — fold that into "actual" before dividing.
- **The BNO055 gyro z over-reports by a few percent, and the amount depends on how it is mounted** (#17). Measured against camera ground truth it is proportional to angle, so a *scale* error, not bias (bias is already removed by `measure_gyro_bias`). Uncorrected, a `CellMotion` turn stops short and 4 turns lose ~6°; with `gyro_scale_z` applied the physical error over 360° was **0.08°**. Any consumer that integrates `imu.gyro[2]` must apply `RobotConfig.gyro_scale_z` (see `cell_move_demo`'s `gyro_rate()`), not just the bias.
- **Re-measure `gyro_scale_z` whenever the IMU is disturbed.** A loose IMU mount was found after the machine started ending turns visibly off-axis and hitting walls; re-tightening it changed the over-report from +1.6 % to +3.3 % (360° error −6.1°, i.e. 1.5°/turn — exactly the symptom). A *tilted* gyro reads `cos(tilt)` times the true rate, so a tilt **masks** part of an intrinsic over-report: 3.3 % × cos 10° ≈ 1.7 %, which is what the first calibration measured. Procedure (in-place rotation only, ~1 min): `cell_move_demo --seq Q,Q,Q,Q --camera-yaw`, then `new = current × true_rotation / estimated_rotation`; repeat 3× — if the spread is large the mount is still loose and no scale value will fix it.
- **An apparent camera offset in the frame is the *tilt*, not the mount — check the CAD before shimming anything sideways** (#87). Where the cell centre lands in the frame is `mount offset + h·tan(tilt) + placement error`, and at h = 340 mm a 4° tilt moves it **24 mm**, which swamps everything else. Reading that as a mount offset sent me to the wrong fix twice. The CAD settles the mount with no measurement at all: the chassis document origin *is* the body centre (three motors at r = 27.2017 mm, 120° apart, centroid exactly 0), the roof's Ø3.4 holes match the chassis's Ø3.2 holes exactly under `body_x = 53.75 − sketch_x, body_y = 38.55 − sketch_y`, and the camera's Ø2.5 holes land on `(0, ±10.5)` and `(12.5, ±10.5)` — the 21 × 12.5 mm Camera Module 3 pattern. The mechanical drawing puts the lens on the board's lateral centreline and on the *upper hole row*, so **with the lens row bolted to the roof's centre holes the optical axis is at body (0, 0) — dead centre, by design.** The observed 22 mm / 17.8 mm apparent offset matched the measured tilt's prediction (22.8 / 13.7 mm) to 0.8 / 4.1 mm; the residual is how far off-centre the machine was placed. **Fix the tilt, not the position**: 0.84 mm of spacer difference across the 12.5 mm hole spacing is 3.8°.
- **Know which walls a full-FOV measurement is actually using** (#87). At 960×720 the frame covers 3.15 × 2.33 cells, so the two axes no longer see the same thing: the **horizontal** bands are still only the current cell's two walls (±90 mm — the next ones out at ±270 mm fall outside the 419 mm frame height), while the **vertical** bands pick up the neighbours' walls at ±263 mm as well. That matters because the neighbours sit on *other floor panels*, and on this rig the panels do not always close up tight. Restricting the fit to the current cell moved the pitch by 0.29°, the same order as the fit residual. `camera_fov` now prints each band's distance from the cell centre and both estimates, so a panel-gap effect shows up as a disagreement rather than hiding in the answer. Two lines can be *correct* but never *validated* — with an exactly-determined vanishing point there is no residual to check, which is why roll needs the machine rotated 90° to be measured properly.
- **The camera is tilted ~4°, and the wall-top grid is what proves it** (#87, `perception/camera_tilt.py`). The wall tops are an exact 180 mm grid in 3D, so a camera pointing straight down images them as parallel lines; a tilted one images them converging to a vanishing point, and **tilt = atan(f / |VP − principal point|)**. This is scale-free, so it is immune to the maze cell not being exactly square — which matters here, because the free-standing 3D-printed pillars (#65) make the fore-aft and lateral wall spacings differ by ~1.5 % and that alone looks like a tilt in any scale-based test. Measured on two frames taken seconds apart in different sensor modes (640×480 cropped and 960×720 full-FOV): **roll +2.4°, pitch +3.7°**, agreeing to 0.2–0.4° between the two. **Shimming brought it to roll +0.75° / pitch −0.44°** (0.87° total, residual 0.05°), which drops the optical-axis foot offset from 21 mm to 5 mm and the intra-cell scale variation from 1.7 % to 0.4 % — a `cell_offset` bias of 0.36 mm at the cell edge, i.e. done. Two things make further chasing pointless: the fit residual is 0.05–0.06° but *near-walls-only vs all-walls* disagree by 0.16–0.25°, so the method resolves ~0.2°; and a 180° rotation put the **floor's own contribution at roll +0.86° / pitch +0.31°**, the same size as what is left. Adjust the machine below that and you are just tracking the floor. Rule out lens distortion first by checking the band centrelines are *straight*: barrel distortion curves them, perspective does not — measured sag was ≤0.9 px over 900 px, and a straight line at the frame edge (the most distorted place) had 0.05 px of sag. The angle scales with the assumed camera height, so quote it with the assumption (±10 % height → ±10 % angle). Note a 4° tilt makes the scale vary by ±1.9 % across one cell, which biases `cell_offset`. **Roll needs the machine parked ~70 mm off the cell centre to be measurable at all**: the frame is 420 mm tall against a 540 mm three-cell span, so a centred machine sees only two horizontal bands — enough for an answer, never enough to check it. Shifted, the wall at −266 mm comes into view and the third band makes the residual computable. The adjustment itself is easiest split: pitch on the roof rods (89.5 mm between the front and rear mounting rows, so 1° = 1.6 mm), roll on the camera's own spacers (21 mm between the hole rows, so 1° = 0.37 mm) — the roof holes are not a rectangle (front y = ±35.05, rear y = +19.95/−35.05), so correcting roll there means turning all four rods by different amounts.
- **Camera as heading ground truth** (`perception/axis_yaw.py`, `cell_move_demo --camera-yaw`): the red wall tops are long straight lines, so their *orientation* gives yaw without the gyro — **σ≈0.4° on a single frame**, so use `median_axis_yaw` over ≥5 frames (σ≈0.2°); the σ≈0.05° originally recorded here was over-optimistic and made ~1° of camera noise look like mechanical play. `wall_detect --measure N` prints the per-frame spread, so check it before trusting a yaw difference. **+angle = body CCW** (verified with a +30° turn). Only measurable **mod 90°** (the lattice is 90°-symmetric), which is exactly enough for 90°-multiple primitives: the folded before/after delta *is* the physical error. Two traps found the hard way:
  - Do **not** use `minAreaRect` on the red contours — a contour clipped by the image border gets a bounding box snapped to the image axes (reported exactly `0.000°`) and dragged the estimate 6° off. Fit **line segments** (`HoughLinesP`) instead and delete edges along the frame border / exclude-rect boundary, which are artefacts of clipping and masking.
  - Average in the **4θ domain** (circular mean of 4·angle), weighted by segment length; plain averaging breaks across the ±45° fold.
- **L6470 unit gotcha**: the Run/speed registers are in **full step/s** (microstepping does not scale speed); Move / positioning / odometry counts are in **microsteps**. `KiwiKinematics` exposes both (`wheel_speed_to_step_hz` vs `distance_to_microsteps`).

Splitting the mask into its `h1` (H 0–10) and `h2` (H 140–179) halves and colouring them differently is what shows this at a glance; a single-colour overlay cannot — `red_mask_parts()` and `wall_detect --hue-split` exist for exactly that. It stays far under the BACK threshold of 0.25, so nothing needs doing — but note that **`v_min` is what separates tape from wall** (57 vs 193) if it ever does. Re-measure this whenever the cable is re-routed: it is flexible, so which part of it lands in frame changes.
- **Taping the cable turned a false positive into a false negative, and the per-edge threshold then hid it** (#65 → #88). The BACK edge used to need its own 0.25 threshold because the untaped cable faked a band at 0.09–0.12 there. Taped, the cable no longer reads red — it *occludes* instead, and the BACK ROI is the smallest of the four (53 × 22 mm, deliberately shrunk to dodge the cable), so a partial occlusion costs a large fraction. On the first 5×5 search run after the full-FOV move a **real wall read 0.24** and was missed: 0.25 defeated wall detection *and*, through `max(threshold_for(edge), 0.20)`, the path check as well — **two independent defences failed on the same 0.01**. After re-seating the walls the same edge read 0.55 and a full run completed with the map matching truth exactly, so 0.24 was a **badly-seated wall**, not a property of the rig — which is the point: a half-strength reading has to survive the threshold, because walls get knocked and re-seated all day. Enlarging the BACK ROI was tried and is *wrong*: replayed over the 25 saved frames, lengthening it 53→106→140 mm moved the wall readings **down** (0.54–0.59 → 0.46–0.54 → 0.43–0.48), because the extra length adds non-wall area faster than it dilutes the cable. BACK is back to 0.08 and a test now asserts **no per-edge threshold may exceed `PATH_BLOCK_MIN_FRACTION`**, because raising one silently collapses the second defence. The general lesson: when you remove an artefact, re-derive the threshold it justified — the artefact's absence does not make a high threshold harmless.
- **The ribbon cable cannot be dodged geometrically — use a per-edge threshold instead** (`WallDetectorConfig.thresholds`; BACK used 0.25 until #88). The cable is flexible: it reads orange (H=7–9, inside the red mask's h1 range) and its position in frame changes run to run, so any fixed "clean corridor" for the BACK ROI eventually fails (it did, twice). But cable ghosts max out at 0.12 while real BACK bands are the widest of all four edges (≥0.51), so the threshold separates them cleanly. Measured per-edge gaps over 113 frames / 452 labels on the 5×5: front 0.000→0.302, back 0.121→0.509, left 0.036→0.344, right 0.016→0.379; zero errors.
- **The LEFT/RIGHT ROI centres ARE the lateral zero point** — `best_roi_red_fraction`'s offset is measured from the ROI position, not from `CALIBRATED_BANDS` (which only feeds px/mm and the regression test). The ~6 mm body-fixed lateral bias (#64) was nulled by centring those ROIs on the measured band centres, verified with ruler-centred poses (readings −6.2/−4.3/−6.2 mm → +0.6/+2.5/+0.6 mm). To re-zero: ruler-centre the machine between opposing walls, read `cell_offset`, and move the ROI centres, not the bands.
- **Wall detection is ROI-based, and the ROIs are calibrated to this exact rig** (`perception/wall_detect.py`, `calibrated_rois()` / `CALIBRATED_RED`). Camera is centre-mounted ~39 cm up and **image top = body forward (+x)**. Since #88 the capture is **960×720 full-sensor** (`Camera.DEFAULT_SIZE`, `DEFAULT_FRAME_SIZE`), which covers 3.1 × 2.4 cells at the *same* px/mm as the old 640×480 crop — so the ROI shapes are unchanged and only their positions moved. **The capture size and the ROIs are one unit**: `WallDetector.measure` raises if the frame does not match `frame_size`, because a mismatch puts the ROIs off the bands and the machine drives into a wall it judged absent (#56). Hard-won specifics — re-check all of these if the mount, height, or lighting changes:
  - Walls appear as bands **inside** the frame, *not* at its edges, so ROIs sit on the bands.
  - The four red **lattice posts are always visible at the corners** (even with no walls) → ROIs sit mid-edge to avoid them.
  - The **camera ribbon cable reads as red** in the lower part of the frame → the BACK ROI is offset left to dodge it (`WallDetectorConfig.exclude` can mask fixed self-occlusion too).
  - The right-hand wall is **washed out, not shadowed** (#56): its red-hue pixels measure S≈46–54 / V≈174–203 (the left wall is S≈179) — pale pink, not dark maroon. So `CALIBRATED_RED` loosens **saturation** to `s_min=50, v_min=40`; `red_wall`'s stricter defaults miss it entirely. Don't "fix" this by lowering `v_min` (the pixels are bright) or by switching to a redness metric like `R − max(G,B)` (washed-out red scores low there too — measured *worse* than the current mask). The root cause is exposure: on the old black-panel floor AE opened up and blew out the bright wall tops (#21).
  - On the wood floor the failure moved from saturation to **hue** (#65 → #78): AE stops down (brighter scene), saturation recovers (S=94–190), but parts of the same right wall drift magenta to H=141–155 — outside `h2_lo=160` — losing the top ⅔ of the band. `CALIBRATED_RED` widened `h2_lo` to 140 (fraction 0.155→0.442, saturating), and **#78 took it to 125**, which is where the weakest wall stops improving. Measured over 90 wall bands from one 8×8 search run: **band saturation is a continuum from 70 to 213 and hue tracks it** (S 70 → H 131, S 198 → H 169; largest gap 12, so this does *not* split into two wall lots), and the weaker a band read at 140, the more of it sat below 140 — 81 % of the 0.092 band, 53 % of the 0.176 one, 4–20 % even of the strongest. Sweeping `h2_lo` with `wall_detect --batch` moves **only the wall side** (weakest wall 0.092 → 0.443 by 125, flat thereafter) while the no-wall side holds at 0.003 until **115**, where it starts to rise: that leak is the machine's own **blue wiring**, whose hue puts 63 % of its coloured pixels in H 100–115 and only 1 % in 120–140 (FRONT/LEFT ROIs overlap the machine, so it is not a distant concern). 125 is therefore both the saturation point and 10 clear of the leak. **Confirmed on hardware by re-running the same 8×8**: weakest wall per edge front 0.176→0.402, left **0.092→0.446 (1.1× → 5.6×)**, back 0.373→0.539, every no-wall edge still 0.000, zero misses and zero false alarms on 204 labels, and the run was otherwise identical — same 22 moves, 20 stops, same map, same 20-cell / 15-leg route at cost 36.8, same 34 s. The only edge that fell is `left:left` (0.551→0.441), and that is **geometry, not colour**: in both runs the two weakest far-band readings are the two cells where the machine's lateral offset cannot be measured at all (no lateral wall to measure it against), and between the runs they moved in *opposite* directions (0.551→0.441 at (4,6), 0.689→0.815 at (6,5)). Worth remembering as a property of #89: **a far band's strength is a position measurement in disguise, and it is weakest exactly where position is unknowable.**
  - **The full-FOV move measured clean on hardware** (#88): with all four walls, front/back/left/right read 0.43 / 0.53 / 0.48 / 0.47; with the back and left walls removed, those two read **exactly 0.00** — the ribbon-cable ghost that forced BACK's own 0.25 threshold (#65 measured 0.09–0.12 there) is gone, so every edge now clears its threshold by 5–6×. Keep BACK at 0.25 anyway: the cable is flexible and where it lands changes run to run, and the margin costs nothing at 0.53. Position repeatability was 0.0 mm over 5 frames — note that is *quantised*, since `search_step = 2` px = 1.18 mm sets the resolution. Axis-yaw spread over 5 frames dropped to 0.11–0.26° (σ≈0.1°, against the σ≈0.4°/frame recorded for 640×480) because the wider frame gives the line fit longer wall segments.
  - **Fixing the camera tilt moves every band — re-calibrate straight after** (#87 → #88). Taking the tilt from 4.3° to 0.87° moved the FRONT/BACK bands by **41 px**, leaving the old ROIs with **zero overlap**: the machine would have missed both walls entirely. The calibration is now derived from two measurable numbers (`CameraGeometry`: where the cell centre lands, and px/mm from the 180 mm band spacing) rather than a table of pixels, so re-doing it is one `camera_fov --emit-bands` run with the machine ruler-centred. That run also *checks* the placement: with the lens on the body centre (CAD, #87) and the tilt nulled, the cell centre must land within a few mm of the optical axis — measured 2.8 mm and 1.5 mm, which is the CAD claim confirmed end-to-end.
  - **ROIs must sit on the red bands, and the bands moved when closed-loop motion arrived** (#56). `CALIBRATED_BANDS` records the band positions measured from frames where `CellMotion` parked the robot (±1 mm): FRONT y=126–143, BACK y=425–445, LEFT x=176–194, RIGHT x=464–490. #16's ROIs came from hand-placed shots and were ~15–20 px off for RIGHT and BACK, so a real wall only filled half the ROI → red fraction 0.08–0.15 → **the machine drove into a wall it had judged absent**. To re-check, take the column (or row) profile of `red_mask` and see where the band actually is; `tests/test_wall_detect.py` asserts each ROI contains its band.
  - **A fixed ROI is not enough: the detector searches for the band** (`search_px=40`, `best_roi_red_fraction`). The dominant error source is *geometric, not chromatic* — the machine's real position inside a cell wanders up to ~25 mm (≈40 px), which slides a 26 px band clean out of a 46 px ROI. Sliding the ROI ±40 px and taking the max fixed 30 of 31 misses in the survey below. The returned offset (centre of the max plateau) doubles as an intra-cell position measurement — the seed for #54. The nearest *other* band is 292 px away, so ±40 px cannot grab the wrong wall.
  - **Odometry cannot see that drift.** Straight moves are good (≤1 mm over 2 cells, #17) but each in-place rotation slips a little, and `CellMotion` holds position during a turn using odometry, which is blind to slip. A survey with 4 rotations per cell accumulated 5–25 mm of real position error while the estimate still read "cell centre to 0.1 mm". Any perception that assumes the robot is centred must tolerate this until #54 lands.
  - **Calibrate against a full-maze survey, not a few photos** (`scripts/wall_survey.py`). It takes a *known* layout (`Maze.from_ascii`), plans a tour with `flood_fill` over the true map — so it drives without depending on the detector it is calibrating — and writes every frame plus ground-truth labels per edge. Room lighting changes per cell *and* per heading (glossy wall tops reflect the ceiling lamp), so one cell's thresholds do not generalise: the same wall read 0.00 facing east and 0.38 facing west. Measured over 9 cells × 4 headings = 144 labels: walls 0.102–0.55 (median 0.43), open edges 0.000–0.033 → **threshold 0.08, zero misses, zero false positives**. When in doubt lower the threshold: a missed wall is a collision, a false wall is a detour.
- **`l6470.decode_status()`**: all-`0x0000`/all-`0xFFFF` ⇒ no SPI communication (wiring/power/CS), not a real fault; fault bits are active-low; UVLO on the first read after power-up is the normal power-up latch.
